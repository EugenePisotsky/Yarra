# Architecture

Current implementation; gameplay foundations updated September 30, 2026. Use [workflows](WORKFLOWS.md) to operate the tools, [performance](PERFORMANCE.md) to measure them, [experiments](EXPERIMENTS.md) for decisions/results, and [refactoring](REFACTORING.md) for remaining structural work.

Game launch options are parsed once in `app_game/launch.rs` and injected as resources/settings. Shared runtime/rendering libraries do not inspect process arguments or bind experimental keys. [RuntimeSettingsPlugin](../crates/app_game/src/runtime_settings.rs) owns the shared render/feature snapshot and applies it to cameras, materials, atmosphere, vegetation and input. It initializes before output setup and before F1 captures its reset baseline. [PerformancePanelPlugin](../crates/app_game/src/render_audit.rs) composes the optional controls, UI and capture session; game startup and [reproduction routes](../crates/app_game/src/repro.rs) work without it. Diagnostic overrides remain fields of the shared snapshot so CLI/F1/reset/A/B use the same state.

Within [performance diagnostics](../crates/app_game/src/render_audit/performance.rs), `panel` owns layout/input/visibility, `capture` owns launch/reset snapshots and bounded A/B recordings, `telemetry` owns frame/app history and pipeline readiness, and `report` owns statistics, comparison text and CSV export. Capture completion returns an outcome to presentation; the recording session has no UI entities or panel visibility state.

`--diagnostics off|panel|full` controls composition. Full preserves the previous default. Panel installs F1 and frame/app cadence collection without CPU system wrappers or GPU probes; Off omits both panel and timing plugins. The vegetation renderer no longer installs Bevy's diagnostics recorder itself; game/editor composition chooses it explicitly. Renderer workload bookkeeping remains part of rendering, and explicit repro/profile automation still works in Off mode. F1 captures canopy values, terrain macro variation and page gizmos alongside other settings.

Keep data/compiler crates independent of Bevy. Renderers do not own SQLite or editor workflows. Currently `engine` depends on both renderers, atmosphere and `world_db`; `world_db` includes authoring/compiler dependencies; vegetation rendering depends on upscaling for temporal integration. These are real dependencies, not a fully separated gameplay/runtime architecture yet.

```text
content/world.project.sqlite
  → bounded source snapshot + environment compilation + world cooking
  → staged, validated runtime publication
  → assets/generated/world.runtime.sqlite
  → read-only database worker → asynchronous decode
  → bounded attachment/removal → renderers and gameplay consumers
```

The editor overlays unsaved source edits on the published runtime. Save changes source; publication creates a new immutable generation. Failed publication leaves the previous generation usable. Runtime pages are derived products, not authoring state.

## World, source and persistence contracts

[world_db](../crates/world_db/src/lib.rs) keeps its public API at the crate root. `records` defines data contracts; `project` separates bounded editor reads/writes from whole-document import/export; `runtime` separates immutable reading from whole-build/incremental output writes. `catalog`, `page`, `storage`, `limits` and `error` own shared encoding, validation and budgets. `cook_store` owns only the bounded source snapshot. Existing environment, road, atmosphere and terrain stores retain their domain transactions and queries. These are internal modules; runtime-only dependency packaging remains future work.

- Stable IDs identify worlds, definitions, assets, placements, presets, layers and roads. Visual entities are disposable representations of those identities.
- Logical positions use world/cell coordinates; render transforms are relative to a floating origin. Rebasing must preserve world-aligned texture, wind and canopy phase.
- `init` creates the Phase 0 [island](../crates/world_cook/src/island_fixture.rs): a ~28 km² island with a 745 m massif, centred in an 8,192 m square of sea. [Imported heightfields](../crates/world_cook/src/heightfield_import.rs) build the same kind of world from a terrain tool's export ([terrain_world](../crates/world_cook/src/terrain_world.rs) holds what they share). Both use 32 m cells with 1 m heights and 1 m paint, a sea level and composite minimum level 2. Exactly flat cells (open sea) store neither heights nor paint. A world may record a start view (project settings, copied to runtime metadata outside the content hash); without `--start-view` the game adopts it when the runtime opens and moves the player and camera there, and the editor focuses it. An import writes cells in place ([terrain_import](../crates/world_db/src/terrain_import.rs)), advancing revisions only where heights or paint changed and never deleting a paint revision, so re-imports cook incrementally. The small 8 m authoring world is `create-road-demo`. Cell size is per world; `DEFAULT_CELL_SIZE = 32` is not proof that every world uses that grid.
- Current versions: source **26**, runtime **25**, page payload **9**, terrain node **2**, recovery journal **14** (reader accepts journal 12–14). Source/runtime constants live in [world](../crates/world/src/lib.rs); journal versions in [journal](../crates/app_editor/src/journal.rs). Incompatible source formats are rejected, not silently reset.
- Editor reads/writes are bounded and revision-checked. Undo/redo uses stable-ID commands. Save commits coherent revisions; stale writes report conflicts. Recovery is separate from ordinary save.
- Production cooking uses one consistent source snapshot, bounded cell/halo batches and staged output. Cell compilation and the material bake's leaf cores, parent cores and finished tiles run on every core in fixed batches ([parallel](../crates/world_cook/src/parallel.rs)). Inputs are read and results written on the cook thread in key order, so the publication is byte-identical to a sequential cook. `cook` prints phase times. Whole-document helpers remain fixture/parity references and share compilation code with production.
- `cook` continues the previous publication when its global inputs (the header hash over catalogs, profiles and environments) and its set of terrain cells are unchanged. It clones the runtime (copy-on-write on APFS) and recompiles only cells whose input fingerprint changed: the cell's source, its 3×3 halo of heights, paint and roads, and its placed objects. Only cells whose ground page changed replace their terrain leaf and its ancestors; a change of the world's hierarchy grid resolution replaces every node in place. Composites re-bake only cores with a changed cell beneath and re-finish only tiles whose 3×3 neighbourhood holds a core that changed. Clean cores come from the cook cache by the fingerprints the runtime records in `terrain_cores`. A clean core missing from the cache, or a different bake library, bakes that space afresh. `cook --full` rebuilds everything. Tests check that both paths publish identical content hashes.
- Unloaded source is unknown, not empty. Road/coverage queries must certify sufficient bounds/halos before compilation.
- Schema or bincode enum changes require explicit version/recook decisions. The old `TerrainRender` payload is still readable, while current cooking emits `TerrainHeightfield`; deleting its enum variant casually would shift serialized discriminants.

## Standalone gameplay foundations

The gameplay libraries are implemented and runnable without Bevy, game/editor startup, cooked worlds or art assets. The game and editor do not depend on these new systems yet. [The content CLI](../crates/game_content/src/main.rs) exercises inventory, trading, actor attributes, equipment, dialogue, Fluent and complete save/load together. [Workflows](WORKFLOWS.md#standalone-gameplay-and-saves) contains the commands.

```text
game_types (IDs, keys, text references, logical time)
    ↑ rules                     ↑ dialogue    ↑ quests
    ↑ inventory → rules         ↑ actors → rules
           ↖       gameplay       ↗
                   ↑      ↑
        save (SQLite state/slots)  localization → game_types + Fluent

engine/apps (future): compose session, saves and localization with Bevy/UI
```

Dependencies follow ownership. `rules`, `inventory`, `actors`, `quests` and `dialogue` never call each other's services or open databases. Inventory consumes rules-owned effect descriptors; actors consume rules-owned source attributes and skills. Dialogue knows only stable IDs, text and condition/action references. `gameplay` supplies those references' meaning and coordinates the domains. No domain imports Fluent or stores rendered translations. `localization` is independent of gameplay and storage.

### Shared contracts and authored content

`game_types` owns durable typed UUID identities, validated semantic `Key` and Fluent `TextKey`, scoped `TextRef::Message`/`Literal`, typed `TextContract` and conversation-local `BindingId`, `OwnerRef`, and `GameTime`. UUIDs serialize as canonical strings in RON/JSON and remain 16-byte blobs in relational identity columns. Semantic maps reject duplicate keys instead of silently overwriting them. Text IDs are independent of editable item/category keys. Authored labels use message references; player-entered names can remain literal text. SQLite adapters serialize these contracts; they do not define a second gameplay model.

`GameContent` contains a manifest, the item catalog and `GameDefinitions` (rules, actor templates, quests, interaction profiles, named predicates, dialogue graphs, campaign facts and action/condition bindings). Validation checks local contracts and cross-domain references before constructing a session. The manifest identifies a content generation and an immutable world publication. A fingerprint covers the exact authored definitions, rules and world binding. `.ftl` translations are independent of that fingerprint, so translation fixes and locale changes do not migrate mechanical saves. Checkpoints contain the mechanical fingerprint/manifest and mutable state; `ContentLibrary` retains the required immutable publication separately. `GameContent` remains the full authoring aggregate and the typed shape of an operation's resolved content subset, not a session-owned complete catalog.

### Authored projects and publication

`game_content` is the outer I/O/composition layer; no domain depends on it. [The checked-in project](../content/gameplay/demo/project.ron) uses source format **6**: explicitly listed packages, one graph/bindings/text directory per conversation and package-owned catalog fragments/templates/rules. Stable IDs, rather than paths or package order, determine identity. Cross-package references require declared dependencies; cycles, duplicate identities and missing targets fail validation. Conditions/actions are indexed by conversation UUID plus local key. RON and Fluent remain authoring sources; gameplay opens published SQLite only.

Content schema **6** publishes categories, items, actor templates, rules, quests, profiles, named predicates, dialogues, derived dialogue contracts, claim definitions, placed objects, areas, triggers, conditions, actions, facts and **text contracts**, with indexed `(kind,id)` keys, bounded 2 MiB payloads, checksums, canonical positions and dependency indexes. It includes no Fluent source. The scenario is a tool-only record. Language-pack schema **1** independently publishes one locale's indexed Fluent resources, contract hashes and translation review metadata. Both builders stage a transaction in a sibling file and publish without clobbering existing paths. Wording edits require no mechanical rebuild and do not change save compatibility. Contract changes do.

The scoped localization implementation uses `(TextResourceId, TextKey)` references and typed `Text`/`Number`/enum-selector arguments. Explicit imports define a scope and reject ambiguous names. Publication analyzes every branch/reference/attribute and detects cycles, undeclared variables, selector mismatches and unsupported functions. Source messages are required; incomplete translated dependency closures fall back as whole messages. Source dependency hashes mark affected translations for review. Development locales warn; declared shipping locales require complete, reviewed coverage. Static labels do not accept arguments. Dialogue graphs declare speaker roles and typed argument sources. Their read models bind actor names, derived attributes and constants into locale-independent `BoundText`; the central formatter renders it. Functions are intentionally unregistered; positional term arguments are unsupported.

`LanguageRepository` opens metadata only and fetches one checksummed resource by ID. `LanguageSource` adapts content contracts and selected packs to the central localization port. `Localization::with_source` loads/parses only requested scopes and locale candidates. Its default LRU holds 32 scopes, at most 32 resources/import closure, and 32 MiB charged data (16 times source/contract bytes plus fixed overhead); active `TextScope` handles pin entries. Preparation is additionally bounded to one scope budget. The authoring constructor allows 64 MiB. These are conservative budgets, not measured heap usage. Providers are immutable snapshots: a new service activates new pack generations without sharing stale parsed caches. I/O remains synchronous and belongs on a worker during engine integration.

[`ContentRepository`](../crates/game_content/src/repository.rs) opens a read-only SQLite snapshot, checks bounded manifest/schema metadata and prepares indexed queries. Opening does not load assets, scan catalog references, parse Fluent or run a scenario. `list` uses bounded keyset pagination over headers; `load` deduplicates an explicit batch and resolves its mechanical dependency closure through indexed point queries. Each requested payload is checked for length, checksum, matching identity, local validity and agreement with the dependency index; resolved records receive cross-domain checks. Text contracts are fetched explicitly; normal mechanical requests do not fetch them or load any wording. Language repositories separately fetch resources by ID within a selected locale. Publication/authoring validation checks the whole project; runtime checks what is requested.

`AssetSet` exposes borrowed typed records and carries its publication hash. It pins entries in a repository-local LRU cache until dropped; cache pressure cannot invalidate active results. A request that cannot fit its dependency set or encounters a missing/corrupt asset returns an error without a partial set. Separate repositories never share cache entries. The reader is synchronous and intended for an I/O worker; asynchronous admission/worker integration belongs to application composition. `ContentRepository` implements the session's `ContentSource` port. Engine worker/admission integration remains future work.

Default limits are an 8 GiB bundle file, 2 MiB per asset, 128 request roots, 256 resolved records, 512 cached records and 32 MiB of conservative cache charges (`16 × encoded bytes + 4 KiB` per record). Charges reserve headroom for decoded allocations/temporary work; they are not measured heap/RSS figures. SQLite separately uses a 512 KiB page-cache target with memory mapping disabled. Per-record dependencies are limited to 256. Header pages contain at most 128 rows; requests above budgets fail explicitly. Counters distinguish header/payload/dependency queries, bytes read, decoded records, hits, evictions and current/peak cache charges. Caller-created copies and the total process allocator are outside these cache counters.

`LoadedProject::materialize_bundle_for_tools` is deliberately eager and used only by `validate`/`demo`: it imports every mechanical asset with aggregate tool limits, verifies the complete publication and mechanical fingerprints, and executes scenario validation. The ambiguous `open_bundle` API is removed. `inspect` exercises the bounded reader. Mechanical fingerprints exclude translations and new-game setup; publication hashes additionally cover the scenario and canonical asset hashes. Source paths are absent from publication identity. Central save schema **7** uses bounded working state and content references. The demo still imports authored setup/presentation eagerly, but its gameplay commands now run against the indexed repository and it retains the content needed by its slots.

Source reads retain a 64 MiB aggregate budget, 16 MiB per RON document and 2 MiB per Fluent resource. Materialized item/game/scenario documents and combined translations retain their authoring limits; these are distinct from runtime working-set budgets. Published payload encoding can exceed a source file's size, so a source-valid resource can still fail the per-asset publication limit. Failed builds remove staging files and preserve previous generations. Older source/bundle schemas are rejected without compatibility loading. `materialize_with_languages_for_tools` explicitly adds eager language-pack validation.

### Scalable dialogue and localization design

This is the target design for a complete game. Indexed immutable storage and bounded runtime opening are implemented above; packages, scoped message contracts and independent language packs are implemented above. Quest/objective state, directed relationships, reusable predicates and NPC opening/topic selection are also implemented. Role-bound lines, explicit repeats, scoped history and reward claims are implemented below. Remaining milestones include events, triggers, ongoing actions, scripting when justified, and world/editor integration. Runtime commands now resolve bounded content/state sets and checkpoints reference retained generations. Authoring/import/report tools still materialize complete projects. Runtime graphs now use explicit repeat policy independently of reward claims; spatial gameplay remains a separate integration gate.

**Authored assets and packages.** Keep authored content centrally under `content/gameplay/<project>`. A project manifest declares content packages; each package owns bounded assets and explicit dependencies. Package manifests declare the asset roots/types they include, with deterministic discovery, strict validation and an authoring-path index. Filesystem order must not determine precedence. Duplicate asset identities are errors; no silent load-order override mechanism is implied. Reuse this boundary for item collections, actor templates and other authored systems rather than maintaining one compulsory file for each system.

A dialogue asset is one coherent conversation. Its directory owns the graph, speaker-role declarations, local conditions/actions, localization argument contracts and locale resources. A quest can contain several conversations. One NPC can offer several dialogue entry points, and a reusable conversation can be bound to different actors. Do not use an NPC's name or a path as the identity of a dialogue.

```text
content/gameplay/main/
  project.ron
  packages/
    core/
      package.ron
      items/...
      actors/...
      localization/common/
        en.ftl
        uk.ftl
    village/
      package.ron
      dialogues/
        old-gate/
          dialogue.ron
          bindings.ron
          messages.ron
          locales/
            en.ftl
            uk.ftl
        innkeeper-introduction/
          ...
  tests/
    scenarios/
      old-gate.ron
```

The directory layout groups work; stable asset IDs determine references. Moving a directory or reorganizing source files must not change a dialogue's identity or mechanical hash. A compiler resolves local references, checks declared cross-package dependencies and produces a canonical dependency graph. Hashes depend on semantic content and dependency identities/versions, not authoring paths or filesystem enumeration. Meaningful order, such as the order of displayed choices, remains part of the asset.

**Editor and source of truth.** Retain RON as the canonical, version-controlled source for structured gameplay assets and Fluent as the source for translations. RON supports structs/enums and comments through the [RON/Serde format](https://github.com/ron-rs/ron); it does not define our authoring workflow or runtime storage. The editor manipulates typed authoring documents and saves these same files. A local SQLite index can accelerate editor search and dependency queries, but it is derived and rebuildable, not another independently editable authority. Published SQLite packages are also derived. Gameplay never opens RON or the source tree.

```text
editor forms / dialogue graph / condition builder ↔ authored RON + Fluent (Git)
                           ↓ shared validation and compiler
              indexed immutable SQLite content + language packs
                           ↓ bounded repository queries and caches
                          gameplay
```

Give authored documents an explicit schema and stable field/variant names rather than exposing incidental Rust runtime struct layout. Reuse domain values and validation; a compiler lowers authoring conveniences into runtime records. RON can be replaced at this boundary without redesigning inventory or dialogue execution. Preserve stable IDs and deterministic formatting, save only affected assets, and detect external edits using source revisions before overwriting. Save groups spanning files need recoverable staging/journaling; publication reads a coherent validated snapshot. Writer notes/translator context are explicit fields, not information that must survive only in parser-discarded comments. Layout metadata such as graph-node positions is saved separately from mechanical content and excluded from mechanical hashes.

Editor Save writes authored source; Save & Publish additionally validates/cooks a new immutable generation. Preview uses the same compiler and runtime contracts on a draft generation. An inspector should expose references, condition errors and selection explanations without requiring authors to write RON. Existing terrain/world authoring remains SQLite-backed: the project can compose different source stores, with explicit ownership and stable cross-store IDs. Choosing text for gameplay does not imply exporting dense terrain to RON or introducing bidirectional RON/database synchronization.

**Dialogue contracts.** Keep durable `DialogueId`, graph-local node/choice IDs, and stable line identities. Separate graph control flow from the lines spoken at a node: a node can contain a sequence of lines spoken by different declared roles. Bind roles such as `player`, `guard` and `companion` to actor IDs when starting an interaction. NPC interaction profiles select eligible conversation entry points through conditions/priorities; a conversation does not own NPC instances. Declare participants and argument sources so publication can check roles and references before runtime.

Keep graph-local conditions/actions with the conversation and resolve them through that dialogue's namespace. Shared rules/facts/items/actions are referenced or explicitly imported by identity; a second global `bindings.ron` must not become the new monolith. The pure dialogue crate continues to own control flow and references. Gameplay owns evaluating conditions, resolving actor/item/rule facts and staging effects. Fluent never drives conditions, rewards, checks or graph traversal.

Separate an active conversation instance from durable dialogue progress and reward claims. Reopening greetings, repeating shop options and returning through a hub must work. An authored choice's availability/repeat policy is explicit; a record that a choice was seen is not itself a permanent prohibition. Claim identities/scopes (for example a quest reward per playthrough, or a reward per actor) prevent duplicate consequences in the same atomic gameplay transition. NPC-specific progress belongs to its declared actor/interaction scope; shared quest facts remain campaign state. Multiple instances of a reusable dialogue must not accidentally share completion state.

**Selecting an NPC interaction.** An interaction profile owns entry rules independently of conversation graphs. Each rule declares a stable identity, trigger/intent (explicit talk, proximity greeting, ambient bark, etc.), participant roles, a typed condition, explicit precedence, repeat/cooldown scope, and a target dialogue/entry node or presentation variant. NPC templates provide defaults; instance assignments and quest-authored contributions add explicitly identified rules. Compile target/trigger/quest-activation indexes so a quest can contribute an NPC conversation without editing a giant NPC file or requiring a scan of every quest/graph during an interaction. Undeclared overrides and duplicate rule identities remain errors.

Use one bounded, typed condition language for entry eligibility, graph branches and choice availability. `All`, `Any` and `Not` combine predicates over declared values: quest/objective status, an actor's remembered outcome, scoped interaction history, directed relationship scores, faction standing, inventory, skills, party membership, location and logical time. Predicates are read-only, have explicit argument types/scopes and bounded evaluation cost, and do not open databases or consume randomness. The composition layer gathers the required facts into a consistent snapshot; a value not yet loaded is pending/error, never an implicit false or zero. Missing asset references are publication errors. Domain-specific extension points should be typed/versioned, not arbitrary scripts hidden in RON strings or Fluent messages.

For example, an explicit Talk interaction might resolve through these authored tiers (illustrative priorities, not universal engine rules):

| Priority | Eligibility | Result |
| --- | --- | --- |
| 100 | Reward ready and the quest's reward claim is absent | Reward conversation |
| 80 | Quest active and this NPC remembers the player's refusal | Refusal follow-up |
| 70 | Quest active and the introduction was completed | Progress reminder |
| 60 | Quest available and introduction not completed | Quest offer |
| 20 | No higher rule eligible and NPC attitude is hostile | Hostile greeting |
| 0 | No higher rule eligible | Ordinary greeting/topic hub |

Writers explicitly decide whether hostility blocks all talk or merely selects a greeting; the condition system must not guess this policy. Several active quests may expose several topics in a hub. Entry selection chooses an opening; topic discovery collects eligible offers instead of hiding every lower-priority quest permanently behind a single winner. Short greeting variants can return to one shared topic hub rather than duplicating the full conversation graph for every greeting.

Resolve an interaction in a defined order: retrieve relevant rule headers, gather their state dependencies, evaluate eligibility, choose the highest eligible priority tier, and resolve any declared selection group within that tier. Deterministic groups have authored tie order; weighted groups explicitly allow random choice. Reject ambiguous equal-precedence rules at build time unless a tie policy is supplied. Randomness never allows ordinary chatter to bypass a mandatory quest scene. Cooldowns and recent-variant history are saved with a declared scope; a pool declares what happens if repeat avoidance excludes every member (for example suppress a bark or relax only the immediate-repeat exclusion). An empty/zero-weight pool is not silently retried in a loop.

Selection previews and eligibility checks do not advance RNG. Starting an accepted interaction commits its selected rule/variant, active conversation and history/RNG updates together; request identity prevents a retry from starting twice. Failed starts leave all of these unchanged. Use explicit saved random streams for narrative selection versus mechanical checks, so cosmetic greeting variation does not change combat or skill-check outcomes. Persist the chosen variant through save/load and locale changes instead of drawing again on every UI refresh. A proximity event needs re-entry/cooldown scheduling; it must not repeatedly start a conversation each frame while the player is nearby.

History distinguishes started, line presented, choice accepted, completed and interrupted. Each event has a defined commit point, so cancelling before a reward cannot mark it claimed or accidentally mark an introduction completed. Store queryable progress summaries with bounded recent-variant lists rather than scanning an unlimited transcript. Quest state owns quest progression; relationship state owns directed scores such as NPC-to-player trust or affinity; dialogue history owns interaction outcomes. Conditions explicitly distinguish world truth from what a particular NPC knows. Gameplay supplies those facts to the pure selector and coordinates accepted actions/quest/relationship changes in one transaction. Quest and relationship implementations should remain separate domains as they grow; neither imports the dialogue service.

The editor needs a "why this conversation?" inspector showing candidate rules, failed predicates with their observed values, precedence decisions and any committed random selection. Scenario fixtures should cover concurrent quests, interrupted introductions, previous choices, attitude thresholds and repeat avoidance. The same selection contract drives tests, editor preview and gameplay.

**Optional scripting boundary.** Keep built-in typed conditions/actions and named reusable rule compositions as the normal authoring tools. Reserve explicit script entry points for logic that becomes clearer as a function: a bespoke evidence calculation, unusual quest consequences, encounter setup or specialized item behavior. Do not gradually add loops, mutable variables and general functions to the RON condition tree; RON describes assets and references functions, while an established language can implement them. The extension is shared by gameplay systems rather than embedded inside the dialogue crate. This is a design boundary, not an implemented VM or a commitment to add a scripting dependency before a concrete authored use case exists.

The relevant precedent is a hybrid: [The Witcher 3 REDkit](https://cdprojektred.atlassian.net/wiki/spaces/W3REDkit/pages/1189412865) exposes script nodes and scripted quest conditions; [Larian's Divinity Engine Osiris](https://docs.larian.game/Osiris_Overview) exposes events, queries and calls in a declarative story system. [Ink](https://www.inklestudios.com/ink/) is a narrative language with its own authoring/runtime model, so adopting it would be a separate decision about dialogue authoring rather than a drop-in general-purpose script extension.

Lua through [mlua](https://docs.rs/mlua/latest/mlua/) is the first candidate for the general-purpose extension; [Rhai](https://rhai.rs/) is a Rust-oriented alternative. Choose one only after exercising a real condition and an action against the same host contract on the supported targets. The host API, transaction/state ownership, diagnostics and resource limits matter more than syntax. Put the selected VM in an outer adapter crate, keep VM-specific types out of domain APIs, and inject the adapter at application composition. A Lua-backed and a built-in condition must be interchangeable from the dialogue selector's perspective.

Keep two explicit entry-point contracts:

- **Predicate:** receives immutable, bounded context and typed parameters; returns a boolean or a diagnostic error. It cannot mutate gameplay, draw random numbers or perform I/O. Errors are not ordinary false results and must be visible in editor/runtime diagnostics.
- **Action planner:** receives immutable context and returns a bounded sequence of existing typed gameplay effects. The coordinator validates and stages them using the normal domain operations, then commits them with claims, history and any authorized RNG changes. Script errors or invalid effects leave the session unchanged. Scripts cannot bypass inventory invariants by mutating item tables directly.

Snapshot inputs declare their dependencies and scope (for example the current quest, participant pair and a bounded set of witnesses). The host resolves these through the same asynchronous repository/state-read path as built-in rules before invoking a function. Scripts receive no SQLite connection, Bevy world, unrestricted actor iterator or filesystem/network API. Bounded host queries operate only within the supplied context, with undeclared/unloaded data reported explicitly. This prevents an apparently small condition from loading the whole world through hidden queries. Runtime validation/tests remain necessary: a compiler cannot prove every behavior of an arbitrary script.

Calls run with operation, allocation, host-call and result-size limits; native callbacks and input construction need their own budgets because interpreter instruction counts do not cover that work. `mlua` provides [memory limits and execution hooks](https://docs.rs/mlua/latest/mlua/struct.Lua.html), but the application must enforce the allowed environment and invocation policy. Invocation state must be isolated so cached modules cannot leak mutable globals or closures between interactions. Host-provided logical time and authorized staged random draws are the only gameplay time/random sources. An initial predicate needs neither randomness nor persistent VM state.

Persistent values belong to explicitly declared, scoped save records, not interpreter globals, live object pointers or serialized coroutine stacks. Long-running sequences should advance saved steps in response to events or logical timers; they must not require a suspended VM stack to survive a save. Returned presentation requests carry stable localization references and arguments; Fluent remains the owner of translated text. Mechanical script changes participate in content-generation/save compatibility just like changes to authored actions.

Keep script sources in Git beside their owning assets or in an explicitly shared package. RON references a stable script asset ID/export and typed parameters, not an inline code string. Publication checks syntax, export contracts and declared dependencies, packages modules with hashes/API versions into indexed SQLite records, and retains source locations for diagnostics. The runtime loads only required modules with a bounded compiled-function cache. Packaging in SQLite does not require portable bytecode: source can be compiled by the pinned interpreter on first use; any precompiled cache must be tied to its interpreter/build target. Lua itself documents [bytecode incompatibility between versions](https://www.lua.org/versions.html).

Start with built-in and named conditions, then use the first concrete scripting need to validate this boundary before committing to a VM. Required checks include repeated predicate calls with no state/RNG change, missing-context diagnostics, budget termination, no cross-call state leakage, rollback after a partially planned action fails, and equivalent results after save/load. Editor diagnostics identify the script, export, source line and supplied inputs; a script condition cannot offer the same automatic explanation as a simple built-in predicate without additional authored diagnostics.

**Gameplay script API, triggers and ongoing actions.** The host contract has three parts: read-only queries, typed command requests and typed events describing accepted changes or observed world transitions. Script functions use stable actor/object/area/quest IDs and logical world positions. They do not obtain engine entity handles or render-space coordinates. Examples of future requests are `SetDoorLocked`, `RequestMove`, `StartDialogue`, `AdvanceQuest` and `GrantItem`; events include `AreaEntered`, `InventoryChanged`, `QuestActivated`, `ChoiceAccepted` and `ActionFinished`. These illustrative names describe the script-facing target, not current script exports. The implemented typed subset is documented under [World events, objects and ongoing actions](#world-events-objects-and-ongoing-actions).

An authored trigger contains a stable ID, activation scope, event filter, optional condition, a built-in action plan or script reference, and repeat/cooldown policy. Scope can be a quest instance, actor pair, region or playthrough. Once-per-quest/actor/playthrough policies must name their scope explicitly. Compile event-type/target/quest indexes and activate only relevant subscriptions; neither registration nor event dispatch should load every script. Basic triggers can execute built-in commands without invoking an interpreter. The editor presents event, filter, condition, action and repeat policy as ordinary fields.

Define event semantics independently of rendering. `AreaEntered` is a logical outside-to-inside transition, not a frame spent inside, an entity being attached after streaming, or a reload notification. Area definitions use bounded spatial queries; first observation/re-entry, teleports and boundary tolerance have explicit rules. Save or reconstruct occupancy consistently so reloading while inside does not fabricate another entry. The richer inventory-event target includes actual quantity change, owner, acquisition/transfer reason and cause. The current `ItemAcquired` signal identifies actor/definition and fires on a committed net increase in carried quantity; it distinguishes new possession from existing possession, but does not yet distinguish pickup, purchase and party transfer. Stack rearrangement or checkpoint restore is not a new acquisition.

Separate event triggers from maintained conditions. “Player collected the key after the ambush began” reacts to a new acquisition event. “Player has the key while this quest is active” evaluates on quest activation as well as on relevant inventory changes. Likewise, a newly activated quest can explicitly check whether the player is already inside an area. Compile dependency subscriptions for these conditions and reconcile current state when activating them; do not require an accidental future pickup/re-entry to unblock progression. A once-only claim prevents repeated effects when reconciliation finds an already-satisfied condition.

Events from a command become visible after that command commits. Stage critical pending events, action requests and trigger claims in the same accepted session transition as their associated state changes; a save checkpoint captures a coherent boundary including pending work. Engine adapters report logical observations through this coordinator. Dispatch uses bounded queues with deterministic ordering and per-step cascade budgets, rather than nested callbacks that can recursively mutate the session. Retain deferred critical work across frames and saves; overload must produce an explicit pending/failure outcome rather than silently losing a quest event. This requires only pending records and scoped progress, not an unlimited event-sourced history.

Stable event/request/action IDs support deduplication. Record acceptance/once claims with their consequences, so delivery retries and save/load do not repeat rewards or movement starts. This is an explicit processing contract, not an assumption of exactly-once delivery from an engine event channel. Eligibility checks use current consistent state and revalidate before committing, even when the triggering event is older. Invalid plans report an error without consuming a successful-execution claim; repeated failures need bounded retries and diagnostics rather than an endless loop.

Distinguish immediate state transitions from requests that execute over time. Unlocking an unloaded door updates its durable world-object state overlay, which is applied when its region streams in. It does not modify the immutable published definition or require the door's visual entity to exist. Unknown/destroyed objects remain explicit errors; unloaded is not equivalent to missing. A move request records an action ID, actor, destination, ownership/interruption policy and logical timeout. It can be accepted, running, succeeded, failed or cancelled. World availability, pathfinding and the actor controller determine progress and report completion/failure; acceptance is never treated as arrival. Combat/death, competing movement ownership, unreachable destinations and unload/reload each need an explicit policy. An offscreen simulation policy can be added separately; `RequestMove` must not silently become teleportation.

Atomicity covers immediate state changes and acceptance of queued work. It cannot cover seconds of physical movement in one open transaction. For example, accepting “unlock gate and send guard to gate” can commit both the door state and move request together, but a later movement failure does not retroactively undo the door change. If unlocking must happen only after arrival, put it in the success transition. Store sequence instance/step, role bindings, pending action IDs and logical timers; resume/reconcile these after loading without serializing a VM stack or replaying completed steps.

Keep typed contracts and trigger/sequence coordination in the Bevy-free gameplay layer, interpreter execution in the scripting adapter, durable records in central saves, and navigation/locomotion/world realization in engine adapters. The existing engine motor already separates movement intent from presentation, but it is not yet the durable NPC-action service described here. Validate the boundary with one complete scenario: activate a quest, reconcile an already-owned item or wait for acquisition, enter an area, request a guard movement, then unlock a door/start a dialogue only on arrival. Test save/load while moving, duplicate event delivery, unloaded doors, cancellation/failure, and already-satisfied quest conditions.

**Localization ownership and references.** Co-locate source translations with each conversation, as shown above. Keep common vocabulary in explicitly imported localization resources owned by a package. Translation tools can gather these resources into locale-oriented exports/reports; translators should receive speaker, scene and line context without editing graph logic. Distributed source files do not require distributed localization services: all systems continue using one central localization API.

Replace a bare global message key with a scoped reference: `(TextResourceId, MessageId)`. Resource identity survives file moves and message identity survives wording changes. A dialogue can use short local message IDs such as `guard-toll` without colliding with another dialogue's greeting. Do not derive identities from English text, node position, NPC names or filesystem paths. Stable line identity can also anchor future subtitle timing/voice assets without requiring audio support in the initial implementation.

`messages.ron` declares each exposed message's stable ID, typed argument contract, argument sources and writer/translator context. Bindings use controlled context accessors, not arbitrary code: e.g. actor display name, quoted price, an integer item count or a declared grammatical selector. Fluent receives already-authorized values. Supply full sentences and numerical arguments, allowing each locale to choose word order and grammatical forms. Do not assemble translated dialogue by concatenating fragments. Fluent's [variables/selectors](https://projectfluent.org/fluent/guide/variables.html) support this division. For fixed world names and terminology, [parameterized terms](https://projectfluent.org/fluent/guide/terms.html) can express case/gender variants; user-entered names remain literal values and cannot be assumed to have automatically available inflections.

Message contracts describe which variables a translation may use and their types/selector values; translators may omit variables that their language does not need. Validate references, transitive dependencies and every AST branch, not just the branch chosen by one sample formatting call. Missing arguments, undeclared variables, unsupported functions, broken term/message references and cyclic imports/references are errors. Rendering tests with representative arguments complement static validation; they do not prove linguistic correctness.

Keep per-message source revisions and the source revision a translation was reviewed against. Wording changes preserve IDs while marking affected translations for review. This translation workflow metadata is distinct from saved gameplay state and mechanical content versions. Source-language completeness is mandatory. Development can fall back for incomplete translations with bounded diagnostics; release validation should require completeness/review status for the locales declared shipping-ready. A valid source locale is always available.

**Published storage and bounded runtime loading.** Separate authored files, published gameplay content and published language resources. The initial implementation may still use one SQLite gameplay file per package, but its records must be addressable by stable asset ID and type. Store each bounded dialogue graph/binding document separately, with indexed headers, dependencies and hashes; do not put every graph into one `definitions` JSON cell. Normalized indexes plus bounded typed payloads are sufficient—every expression need not become a separate SQL table.

This loading contract applies to items, actor templates, quests and interaction profiles as well as dialogues. The bounded repository is implemented, while `materialize_bundle_for_tools` still reads all content for explicit validation/demo use. Sessions now request resolved inputs through repository lookups/batches. Inventory instances retain definition IDs and mutable quantities/instance properties; load definitions for equipped/carried/visible items or those needed by an accepted operation. Inventory weight/capacity/trade checks must gather all definitions required for that operation, not just those visible in a UI. Definitions shared by multiple instances are cached once per content generation.

Use indexed, paginated catalog queries for browsing and batch ID queries for known inventory entries. Query selection-rule headers without loading their target graphs, then load only the selected graph and required text resources. Schedule SQLite reads/decode outside the frame-critical path; prefetch nearby interaction profiles when useful, with explicit pending/error states and bounded request queues. Pin the bounded dependency set used by an active operation, and release it afterward. Pure domain functions consume resolved definitions/facts and never perform hidden per-item SQL reads. Small explicitly budgeted common tables may remain resident, but catalog growth must not imply proportional resident memory. Bound the application caches, SQLite page caches, payload sizes, in-flight requests and dependency closures; report a budget failure instead of silently expanding them.

Publish localization resources as independently versioned language packs, indexed by `(resource_id, locale)` and carrying message-contract/source revision metadata. A pack can contain all resources for a package/locale; do not open one SQLite file per conversation. One new translation or a wording fix can ship without rebuilding mechanical content or migrating saves, provided the message/argument contracts remain compatible. Pack manifests declare the contract set they satisfy. Changing a contract is explicit and requires revalidation; translations are not arbitrary replacements for gameplay data.

At runtime, load the active conversation's graph and the selected-locale/source-locale resource dependency closure. Cache parsed graphs and Fluent bundles with byte budgets; pin resources for active conversations and evict unused entries. Cache keys include asset/resource identity, locale, revision and imported dependencies. Load common vocabulary through explicit imports into the relevant scope; `fluent-bundle` has [resource/bundle primitives](https://docs.rs/fluent-bundle/latest/fluent_bundle/) but does not supply Yarra's scoped lookup, caching, dependency or publication policy.

Fallback resolves a complete message and its dependencies in one candidate locale. Never combine part of a sentence from one language with a source-language term because a dependency happened to be absent. Try the configured locale chain, then the source locale; formatting defects remain diagnostic errors rather than being silently treated as a successful translation. Switching locale replaces presentation resources while preserving current dialogue position, choices, participants and gameplay state. Other languages and unrelated conversations should remain unloaded.

**Save, command and validation boundaries.** A save references a retained immutable mechanical content generation and stores mutable progress: actor-role bindings, active node/call state, local variables where needed, scoped progress/reward claims, campaign facts and controlled random state. It does not copy every authored dialogue or translation into each slot. Loading requires the referenced compatible content generation; missing content produces an explicit failure. Translation packs have independent revisions and compatible message contracts. If history is persisted, record line/message references plus argument values captured when the line was produced, rather than only rendered text or values re-read from a later world state.

Runtime commands stage bounded changes to the participating actors, inventories, conversation, facts/claims and random state. Validate their references against immutable content and commit/publish one accepted transition. The implemented working store uses record revisions and changes to touched records, preserving rollback and coherent save checkpoints, including unloaded mutable objects. Claims, pending events and world actions share that boundary. This remains a separate responsibility from loading immutable content assets.

Full-project validation belongs to authoring/publication and CI. Runtime opening checks manifests/indexes and validates requested payloads; it must not load every conversation, parse every language or execute a scripted demo. Separate campaign starting-content assets from optional test scenarios. Run scenario exercises through an explicit testing command. Dependency tracking permits incremental revalidation/rebuilds after edits while a full validation command remains available.

Acceptance for the refactor should demonstrate: multiple conversations with identical local message IDs; graph/file moves with unchanged identity and hashes; multiple speaker roles; repeatable greetings plus a reward claimed once; complete scoped localization with typed arguments and source fallback; stale translation reports; changed text with unchanged mechanical save compatibility; and failed changes leaving the previous published generation/session intact. A generated large catalog should prove through loaded-resource/query/byte counters that opening a small inventory or starting one conversation loads neither the complete item/dialogue catalog nor inactive languages. Test quest/attitude/history precedence, topic coexistence, deterministic random selection across save/load, RNG rollback, missing-state readiness, and editor source-conflict handling. Measure cache eviction and dependency invalidation rather than assuming file splitting has made the system scalable.

The dependency-ordered [gameplay implementation roadmap](REFACTORING.md#gameplay-implementation-roadmap) starts with stable asset/text identities and indexed runtime repository access, then bounded session state/checkpoints, modular authoring/language packs, quest-aware dialogue, triggers/ongoing actions and the optional script adapter. Editor/world integration follows the relevant contracts. Adapt fixtures and integration tests along the way, remove superseded prototype formats directly, and preserve the existing transaction guarantees. A game UI can then consume these APIs without depending on source layout or compiler internals.

### Inventory and trading

`inventory` owns categories, item definitions, inventories, stacks, wallets and trade settlement. Categories have stable `CategoryId`, unique editable keys and `TextRef` names. Definitions use category IDs, separate merchant buy/sell prices, tags, weight, stack limits, permissions and rules-owned item mechanics. `None` price means refusal; zero is valid. Category rename preserves item references; referenced categories cannot be removed. Categories and definitions are relational SQLite tables with foreign keys. Vendor/category price multipliers remain a future trading policy, rather than a global category property.

An inventory has a durable owner and role, such as an actor's `carried` inventory or a chest's `contents`. Actors, NPCs and companions use the same identity/ownership model; shared party wallets are explicit. Session validation resolves actor owners and registered external chest/party owners. It rejects duplicate global item IDs, duplicate owner/role inventories and invalid references. Every session actor currently needs a carried inventory, which may be empty.

Domain APIs retain grant/consume/discard, split/merge, filtering, weight totals, item/money transfer and trade quote/commit operations. Stack limit one creates individually identified items and is required for equipment. Full transfers preserve entry IDs unless a compatible stack absorbs them; partial transfers/splits create new IDs. Returned destination IDs identify surviving stacks. Permission and arithmetic failures leave inputs unchanged. Access, control, distance and looting authorization belong to the future interaction adapter.

A trade quote captures the catalog and four participant revisions, validates the basket and previews final capacity/net settlement. Commit recalculates and validates those values, then changes both inventories and wallets together. Accepted quotes cannot replay. Gameplay coordinates equipment references when trading or transferring equipped items. Later vendor-policy revisions must also participate in quote validation.

`inventory_db::CatalogStore` remains an independent authoring API with optimistic revision checks; its catalog read/write adapters require a caller-owned transaction. The superseded inventory-state persistence adapter was removed. `save::WorkingStore` now owns live actor/inventory/wallet/conversation/quest/relationship/interaction/history/claim/object/location/sequence storage, global item identity indexes and checkpoint publication. Authoring schema **4** and central save schema **7** reject earlier formats without compatibility layers.

### Rules, actors and dialogue

`rules` defines data-driven attributes, skills and equipment slots, checked base values, additive modifiers and healing/timed-buff descriptors. Derived attributes sum modifiers before clamping, making results independent of modifier ordering. The rules catalog identifies the attribute governing maximum health. Skill XP is durable; the first dialogue skill-check rule uses a d20 plus one bonus per 100 XP. This is an initial mechanic, not a full progression/combat system.

`actors` uses one common structure for players, companions and NPCs: template ID, optional name override, role, logical position in millimetres, base attributes, health, skill XP, equipped-item references and active effects with absolute logical expiry times. Templates and instance state are separate. Equipment refers to existing carried items instead of duplicating them. Derived stats are calculated from source state when requested and after loading; no derived cache is serialized. World-space/position adapters and spawning remain part of the future engine integration.

`dialogue` validates bounded graphs with stable node/choice keys and holds per-participant/speaker progress. Each choice can reference pure conditions and actions provided by gameplay. Conditions cover item possession, campaign facts, skill XP, quests, objectives and directed attitude, composed with Boolean groups and named predicates. Actions consume/grant items, award XP, set facts, transition quests, adjust attitude or branch on a controlled skill roll. Choices explicitly repeat always, once per run or once in scoped history. Stable claim definitions protect reward groups independently of conversation/choice repetition. Active runs resume; completed/interrupted runs can restart under the graph policy.

`quests` owns pure definitions/progress, required or optional objectives and explicit start/objective-complete/complete/fail transitions. Completing a quest requires every required objective. Terminal quests cannot restart. `actors::Relationship` owns directed attitude with saturating adjustments in −100…100. `gameplay` resolves these domains alongside items, facts and skills; neither domain depends on dialogue, SQLite or Fluent.

An actor template optionally references an `InteractionProfileId`. A profile owns ordered condition rules and weighted dialogue variants. Automatic opening selects the highest eligible priority and lowest explicit tie order; topics are independently discoverable. Named predicates are UUID-addressed assets. Validation shares a resolved traversal with the repository (cycle checks, depth 32, 1,024 visits; each authored tree has depth 16 and 256 nodes). An interaction preview reports each rule's eligibility and observed leaf values without changing RNG or state. All branches are evaluated for diagnostics. Only the chosen graph loads on `Talk`. Profiles load derived dialogue contracts for repeat eligibility and history key validation; contracts contain no graph control flow or wording. Published `asset_links` separately validate actor→profile and profile→graph references.

`dialogue::Interaction` saves the selected profile/rule/variant per participant/speaker pair. Active graph progress resumes rather than rerolling, even if a newly active quest would select a different opening. A separate saved narrative random stream isolates variation from skill rolls. Quest/relationship/interaction records use the working store's indexed keys and revision checks. Explicitly requested absent progress resolves to `NotStarted`, neutral or idle only after a storage lookup; it counts toward the working-set budget and inspection writes nothing. Unrequested state is an error, and unknown quest definitions/actor references still fail validation. History is a separate indexed record keyed by dialogue and declared scope (playthrough, interacting actor, addressed actor or ordered pair). It counts starts, acknowledged lines, accepted choices, completions and interruptions with bounded maps and last-start time. Profiles and choices query this summary without loading historical runs. Claims use independent UUID definitions plus scope, allowing different graphs/NPCs to guard one reward. A claimed action group is skipped on replay, including RNG draws; claiming and effects commit atomically.

Graphs declare roles and ordered lines per node. Active runs persist role→actor bindings, next line, status and run/step token. The public conversation view resolves line/choice text references and typed actor-name/attribute/constant arguments without Fluent. Central `Localization::format_bound` handles wording. Explicit line acknowledgment commits presentation history; choices require all lines acknowledged. Interruptions record no completion, and a restart increments the run token. Tokens on advance/choose/interrupt reject stale UI input after loops or reopening. `Always`, `OnceCompleted` and saved-time `Cooldown` govern graph starts; choice repeat policies remain independent. Required role/message contracts are validated at publication and bounded graph loading.

Current profile scheduling is explicit talk/topic interaction. Ambient/proximity events, recent-variant avoidance and party-role assignment belong to later application/world work; they do not require changing history or claim storage.

### Session commands and atomic transitions

`GameSession<S, C>` coordinates a `StateStore` and `ContentSource`; both ports live in the Bevy/SQLite-free `gameplay` crate. The production adapters are `save::WorkingStore` and `game_content::ContentRepository`. Sessions own no full-world state or catalog. `StateRequest` queries return a bounded read model from one transaction; quote/choice previews are pure. `CommandOutcome` returns the exact committed header and events, avoiding a second state read to identify the result's generation.

A command resolves participating records, their actor/owner/carried-inventory closure, required item/template/graph/rules assets and referenced facts. It clones and validates only that operation's bounded records. Changes use per-record revision checks, item-location uniqueness and one SQLite transaction with a header-generation check. Any rejected consequence/write discards domain state, facts and RNG together; a failed staging transaction cannot commit. There is no persistent decoded state cache: the working database owns resident and nonresident records, while the bounded content repository caches immutable assets. Calls are synchronous and belong on the future application I/O/simulation coordinator, not arbitrary render-thread callbacks.

Using a potion consumes one item and applies its effects atomically. Transferring or selling equipment updates the affected actors and health bounds in the same command. Time advancement uses an indexed expiration queue, processing one affected actor and its dependencies at a time within one transaction. It visits intermediate expiration deadlines so a large time step preserves health caps that would occur with smaller steps. No deadlines means no actor reads. Work limits fail with rollback. Saved SplitMix64 streams separately control skill rolls and conversation variation; previews never roll. A failed roll is an accepted gameplay outcome, while an invalid consequence rolls back the random state. Runtime-created item IDs derive from playthrough, command generation and ordinal, independently of narrative randomness, so replay from a checkpoint preserves identities.

Working sets are limited to 64 records, 8 MiB of encoded input payloads and 1 MiB per mutable record; SQLite has a separate 512 KiB page-cache target and mmap disabled. Up to 100,000 actor expirations may be processed in one time command without holding them together in memory. Decoded objects, the bounded before/after copies and operation content copies consume additional memory; these are explicit processing/accounting bounds, not measured RSS limits. Store counters report decoded records/bytes, peak input working set and staged record writes (including subsequently rolled-back work). Content resolution retains its separate root/closure/cache limits.

`SessionState` is now an operation fragment or explicit authoring seed/tool export. `WorkingStore::create`/`in_memory`, `ToolContent` and `export_for_tools` are eager tooling APIs; commands/checkpoints never call the exporter. New-game scenario construction still belongs to the authoring/import path until packaged campaign starting assets are introduced. Runtime resume/restore and ordinary commands require only indexed state/content. The old session-wide `state`, `snapshot` and `content` accessors were removed.

### Headless gameplay and automation

**Target contract:** the complete mechanical game must be playable without a window, GPU, native input, audio or visual assets. Interactive play and automation drive the same authoritative gameplay and world simulation. Presentation observes that simulation and translates input into its public commands; it does not own dialogue selection, rewards, interaction permission, trigger detection or action completion. Headless execution keeps the world geometry, contact/navigation data and simulation needed to decide those outcomes. Pure domain crates remain Bevy-free; shared spatial simulation may use a headless Bevy app.

This is partly supported today, not yet a full game mode. Standalone session/scenario tests already exercise domain commands, logical time, controlled randomness and saves. Engine gameplay tests manually tick the actual character motor and grounding against synthetic terrain without a renderer. However, `GameplayPlugin` still installs character presentation, `MinimalGamePlugin` installs rendering, and terrain contact readiness is tied to terrain LOD residency. Separate simulation configuration and contact/navigation residency from visual assets, cameras and render demand before claiming production-world headless support. There must be one authoritative owner per state concern, with engine execution reporting through the runtime boundary rather than maintaining an independently mutable copy of saved gameplay state.

Expose three capabilities through application composition: submit typed commands using durable actor/object IDs and world coordinates, query bounded read models, and advance simulation by explicit fixed steps. Commands report rejection, pending work or acceptance; ongoing actions report lifecycle transitions and correlation IDs. Queries expose conversation/choice models, actor progression, inventories, object access and action status without granting mutation or requiring callers to inspect SQL/ECS internals. The graphical UI and automation consume these same models. `Talk` now selects NPC conversations through the domain session; `WorldCommand::Open`/`container_contents` now check logical object access, while physical reach checks and movement execution still need world integration.

| Automation case | Required path and observation |
| --- | --- |
| Talk to an NPC | Submit the ordinary interaction, including reach/access checks and NPC selection. Assert the resulting dialogue, node, speaker, message arguments and available choice IDs. `Talk` tests profile selection; explicit `StartDialogue` tests graph execution. Reach/access checks still need the world adapter. |
| Receive a reward and unlock a chest | Choose through the active conversation; inspect progression and lock state, then invoke the ordinary open-container interaction and inspect its contents. Include rejection while locked and reward replay protection. Directly changing a lock flag does not prove interaction behavior. |
| Enter a trigger area | Request movement and advance the real shared controller/contact/trigger systems until arrival or a bounded failure. Observe the area transition and its consequences. Explicit setup/teleport and injected events are useful narrower tests, but do not replace movement-to-trigger integration coverage. |

The runner owns a fixed step clock, explicit seeds and bounded advance-until predicates/events. It never sleeps to simulate game time. Content/world readiness must be explicit: await required data at defined admission boundaries before dependent steps, and do not let worker completion order decide gameplay outcomes. Use stable command/event ordering and controlled gameplay RNG streams; generated identities must be reproducible or mapped to stable scenario aliases for comparable traces. These controls target repeatable gameplay outcomes, not an unverified promise of bit-identical floating-point behavior across platforms. A separate wall-clock watchdog catches stalled I/O; tick, command, queue and trace budgets bound scenarios.

`HeadlessDriver` now supplies shared command submission, queries, explicit fixed logical steps, bounded advance-until predicates and a capped event trace. It has no separate gameplay rules or spatial simulation. Grow command/query coverage as the actual systems arrive, then extend the source scenario CLI with published-campaign inputs, a bounded failure trace and world assertions. The current CLI supports opening/topic/quest, object, container and pending-movement assertions, a bounded world pump, and exits nonzero on failure. Reuse published SQLite content, normal working-state storage and central manual/quick/auto save APIs. Include save/load midway through conversations/actions, discarded unsaved progress, cold caches and unloaded objects. Keep fixture setup separate from player actions; there is no parallel implementation of gameplay rules in the runner and no Lua requirement for automation.

Headless tests establish the correct conversation model and mechanical consequences. A small graphical suite still verifies that UI widgets display those models, input maps to the correct commands, and animation/camera/presentation behave correctly. Full world acceptance must exercise production movement, contact and loading in both compositions; tests using engine substitutes prove the adapter contract only. Headless support is an acceptance criterion throughout the [gameplay roadmap](REFACTORING.md#gameplay-implementation-roadmap), not a final retrofit.

### Central saves

`SaveDirectory` supports manual slots, quicksave and rotating autosaves. They use one SQLite format and one validation/load path. Autosaves have a bounded retention group and a persisted sequence for rotation, independent of wall-clock adjustments; they never overwrite manual or quick slots. Calls are synchronous and intended to be serialized by the application save coordinator. Background save scheduling and multi-process directory coordination are not implemented.

Save/working schema **7** stores a small content identity and session header, indexed actor/inventory/wallet/conversation/quest/relationship/interaction/history/claim/object/location/sequence records with payload checksums/revisions, owner and item-location indexes, individually addressed facts, a pending-event queue and exclusive movement/deadline indexes. Definitions, translations and render state are absent. The private working database persists accepted commands without advancing named slots. `WorkingStore::open` rejects a named checkpoint: restore must create a separate working file.

A checkpoint pins a SQLite read snapshot and uses the online backup API in 64-page steps to copy all records, including nonresident objects, into a sibling staging database. After writing slot metadata and closing/syncing the file, atomic replacement publishes the slot. Failed copying/metadata writes preserve an existing slot and clean failed first saves. This copies database pages, not decoded world state, and correctly includes live WAL contents. Checkpoint cost still scales with database size on disk; bounded application memory does not imply constant save time.

`ContentLibrary` retains immutable SQLite publications by mechanical fingerprint, using snapshot copying and no-clobber publication. There is no automatic content garbage collection. An already-retained mechanical generation is reused; translation packs are selected independently of saved mechanical identity. `SaveDirectory::content_identity` identifies a slot's required generation, and `ContentLibrary::load` resolves it before restoring. Missing content and incompatible content/world identities are explicit errors. Restore copies into a fresh working file, verifies metadata/header consistency and opens a candidate without decoding all records or assets. Individual records, hashes, ownership indexes and domain references are checked on bounded access; this is deliberately not a full-world validation scan on load. Tool export/publication validation remains explicit.

Manual/quick/auto saves share this path. Tests cover discarding unsaved progress, restoring unloaded actors, WAL-backed working stores, RNG/effect/item-ID continuation, failure after record writes and after checkpoint copying, stale record revisions, slot isolation, incompatible schemas/content and requested corruption. Existing `world_db` authoring/runtime formats are unchanged. Authored seed limits remain 10,000 actors, 20,000 inventories/wallets and 10,000 conversations; inventory limits remain 4,096 entries, 1,000,000 units per stack and 256 trade lines. Eager tool export is limited to 100,000 records/64 MiB; checkpoint copying no longer serializes the whole state into that tool budget.

### World events, objects and ongoing actions

The Bevy-free `gameplay::world` contracts are implemented; `world_runtime` coordinates them through the same content/state transaction ports. `ObjectId`, `AreaId` and `TriggerId` identify placed content. Objects, axis-aligned areas and triggers are separate package-owned RON assets published to SQLite. Object names use central `TextRef`/Fluent contracts. Triggers currently bind two placed actor IDs; dynamic spawn/binding instances are future work. `SequenceStep` supports immediate existing domain actions and asynchronous movement. No script VM is involved.

`Maintained` triggers compile subscriptions from all resolved condition dependencies, including named predicates, quests, inventory/skills, facts, relationships, history/claims and area membership. Activation checks current state, so starting a quest while already carrying its item or standing in its area works. `Events` triggers subscribe to explicit edges and do not reconcile on unrelated quest activation. `ItemAcquired` means a net increase of that definition in an actor’s carried inventory in the committed transition; `QuestStarted` distinguishes activation from later objective updates. Subscription `(signal, trigger)` keys give deterministic paginated dispatch without loading unrelated triggers. A reverse index checks a requested trigger's subscriptions against its definition. Area bounds are queried in SQLite with an x-bound index and all three axes filtered; only matching IDs are returned, capped at 32 overlaps. This is a bounded payload query, not a claim of constant spatial-query cost for arbitrarily overlapping regions.

Accepted state changes enqueue only signals with subscribers. Domain records and checksummed pending events commit together. The queue is capped at 4,096 events, with 256 new signals per command; overflow rejects the command without losing events. `WorldCommand::ProcessNext` processes one subscriber or due movement timeout per transaction. Event cursors persist between deliveries and events are removed after their last subscriber. `HeadlessDriver::pump_world(limit)` reports whether work remains after its budget; there is no recursive callback dispatch or unbounded event history. The application must schedule this pump, including after advancing time.

`ObservePosition` is an authoritative adapter observation with a monotonically increasing per-actor sequence. Identical retries leave domain effects and queued work unchanged; stale/conflicting observations fail. Areas use half-open millimetre bounds. Membership is derived from position; entering/exiting queues typed signals. This is a logical observation boundary, not a navigation/pathfinding simulation. Adapter authors must reconcile their observation counter from saved `LocationState` when restoring.

Objects default from immutable definitions after an indexed absent-overlay lookup. Lock/open/destruction overlays are saved independently of region loading. Querying or unlocking a container does not load its inventory or item definitions; contents are resolved only after an authorized contents request passes the lock check. `Open` rejects locked/destroyed objects. `container_contents` requires an open, unlocked, intact container and resolves its inventory through an explicit object owner/`contents` binding. Unknown object IDs fail; unloaded objects remain accessible to authorized logical commands. Raw inventory transfer and administrative world commands remain trusted APIs; player control, reachability, distance and permission checks belong to the application interaction adapter.

A sequence stores run/step, status, bound definition, pending movement and at most 32 current-run receipts. `ActionId { trigger, run, step }` survives checkpoint restore. Movement has accepted/running phases, an exclusive per-actor lease and a logical deadline. Adapters poll `next_movement`, acknowledge with `StartMove` and report arrival/failure/cancellation through `FinishMove`. Acceptance leaves position unchanged. Arrival must match the destination and occur before the deadline; timeout processing releases the lease. Repeated identical reports are harmless; conflicting reports and older runs fail. Adapters own pathfinding and must report interruption by combat/death/unloading explicitly; no offscreen movement or teleport policy is inferred.

After arrival, subsequent immediate effects commit together. A domain failure rolls those effects back, preserves the already-observed arrival and records a failed sequence with a bounded diagnostic; a storage failure rolls back the whole reporting transaction so the adapter can retry. An invalid initial plan records failure without consuming reward claims. New dependency events may retry failed sequences, up to three consecutive failures; `RetryTrigger` explicitly resets this limit and rechecks eligibility. Cancellation does not count as a failed attempt. Repeat policies are once-successful, always, or a cooldown since the last start. A cooldown throttles incoming events; it does not schedule a timer to start a sequence by itself.

The [guard/gate exercise](../content/gameplay/demo/scenarios/guard-gate.ron) enters an area with an already-owned key, requests guard movement, and unlocks the gate/container and awards the shared quest reward only after arrival. Contract tests use explicit synthetic adapter reports. They cover manual/quick/auto restore before dispatch and while accepted/running, duplicates, failures/cancellation/timeouts, movement ownership, rollback, edge versus maintained activation, corrupt indexes/queues and 1,000 unrelated trigger definitions. Production navigation, contacts, streaming realization and graphical integration remain milestone 7.

### Fluent localization

`localization` wraps [`fluent-bundle`](https://docs.rs/fluent-bundle/latest/fluent_bundle/) with thread-safe bundles and `unic-langid`. Runtime callers compose an indexed resource provider and request an explicit locale; authoring tools can supply resource strings. Fallback follows exact locale, language/script, base language, then the source locale; it never selects an arbitrary region. Results report the locale used and whether fallback occurred. Literal user text passes through unchanged. Resource parsing/duplicates, missing messages and formatting/argument errors are explicit errors; malformed partial formatting is not displayed as success.

[English](../content/gameplay/demo/packages/core/en.ftl) and [Ukrainian](../content/gameplay/demo/packages/core/uk.ftl) resources exercise the standalone content. `game_content` owns bounded filesystem loading and validation of complete resource sets. Locale preference, hot-reload orchestration, fonts, shaping and UI layout belong to application/presentation integration. Rebuild and validate a replacement localization service before swapping it into presentation.

## Environment authoring

Reusable typed presets and compositions feed ordered spatial layers with coverage masks. One compiler derives ground palettes/weights, vegetation fields and generated objects. Empty coverage uses the world's explicit base material. Terrain surfaces have semantic IDs; texture-set array layers are resolved during cooking.

Curved roads have stable source geometry and shared styles controlling wheel tracks, center/shoulder wear, vegetation retention and relief. Relief is derived from original source heights, never repeatedly added to previous output. Explicit junctions connect 2–4 compatible arms. Spatial certification, intersections, samples and output work remain budgeted; querying one region must not recursively load the entire route network.

Asset collections deterministically scatter registered visuals with weights, scale/spacing, slope and clearance controls. Generated placements are render-only and are not individually editable source objects. Manual object placements remain separate and preserve stable identity.

Asset management currently consists of local source/runtime files, tracked pack manifests, SQLite asset/LOD records, a searchable editor placement palette and collection selection. `world-cook import-assets` validates a bounded RON catalog and local file availability, then registers stable key-derived IDs transactionally through `ProjectWriter`. Reimports refresh supplied variants and preserve unrelated records, placements and definition aliases. Asset conversion remains an offline tool, without an editor import UI. The Forest Tree Starter Kit summer catalog includes 11 trees and 8 shrubs with four mesh LODs each; licensed binaries remain ignored local files.

## Terrain and streaming

The default terrain hierarchy supplies distant coverage, bounded material streaming, smooth geometry transitions and nearby detailed shading. `--terrain-legacy` selects the older nearby world renderer for diagnostics; it does not change publication. Normal cooking includes distant material products and requires prepared CPU inputs. `--geometry-only` is an explicit fixture option.

[Database transport](../crates/engine/src/world_streaming/database.rs) owns worker startup, bounded channels and shutdown. Its protocol and immutable-reader queries depend only on `world`/`world_db` data, not terrain-rendering or residency modules. Source and terrain/material consumers submit requests without blocking; the streaming coordinator routes replies and owns world/index state and transitions. [Source residency](../crates/engine/src/world_streaming/residency.rs) separately owns page requests, asynchronous decoding, admission, cooling, statistics and stale-result rejection. A staged generation can answer terrain queries, but source reads remain on the active generation until the exact commit is acknowledged.

Dropping the worker disconnects a separate cancellation channel before joining. Both request and reply waits can then exit even when queues are full; an already-running synchronous SQLite read still finishes first. Runtime worker omission/restart is not a supported streaming mode.

[Attachment](../crates/engine/src/world_streaming/residency/attachment.rs) converts prepared pages into CPU sources, objects or legacy terrain entities, tracking page-owned meshes, materials and images for removal. Whole-page object validation and fallible terrain preparation finish before spawning entities or storing owned assets. Cooling retains ownership for two seconds and can revive the same entities. World/generation changes clear pages and cancel decode jobs without reusing pending request identities; same-world hierarchy rebases preserve canonical sources. These internal systems remain ordered inside `WorldStreamingSystems`; residency omission or runtime suspension is not a supported mode.

Important invariants:

- Cooked heights are f32 values on one world-wide 1/1024 m grid, and normals keep 12 bits per octahedral axis (about 0.05°). Constructors round both, so editor previews, cooked pages and decoded runtime data hold identical values, and shared edges stay bit-identical because the grid never depends on the page. The [codec](../crates/world/src/terrain_heightfield_codec.rs) stores planar-predicted integer steps: terrain nodes and height pages are about 40% of their previous zstd size on the hill fixture. CPU grounding/raycasting and grass placement interpolate the same piecewise-linear triangles as terrain geometry, not a different bilinear surface.
- Parent nodes decimate heights exactly but filter normals (3×3 tent; border samples filter only along their edge, so neighbours share codes). Point-sampled normals made distant lighting change at every level switch.
- Parent coverage must not fill holes. Retain a complete active cover while replacements load; parent/child transitions, stitched edges and morphs must remain crack-free.
- Geometry/material visibility and detailed source demand are separate. Elevated views must not demand finest leaf geometry everywhere below the camera.
- Actor contact outranks vegetation/contact and visual refinement. Grass may be retired atomically under pressure; actor grounding must not disappear. Readiness checks use the drawn surface, including transitions.
- Coarse material fallbacks remain available while fine products stream. `TerrainProfile::composite_minimum_level` limits which composites are published: roots and levels at or above it. Leaves below that level are evaluated in memory and filtered straight to it, so finer cores are never staged. Exception: when a root lies below the level, the space starts at the leaves. Cores at that level and above are cached in `<project>.cook-cache.sqlite`, one entry per node, keyed by node and fingerprint. The fingerprint hashes every evaluation input, so a cook evaluates only groups whose inputs changed; a test checks that the result is byte-identical to an uncached cook. The cache is deletable. Evaluator changes that alter output must change the fingerprint salts, as for the runtime's own fingerprints. Streaming never requests finer tiles, and the editor's live preview evaluates unpublished leaves from their published pages as the cook did. Zero (every level, the default) preserves previous output; each step quarters the finest stored texel density. Near detail uses existing hierarchy geometry, not another coincident ground mesh. `TerrainMaterial` remains shared by near-detail preparation and editor previews even if legacy world rendering is later removed.
- Rebase, source edits, publication and shader changes invalidate the appropriate caches. Obsolete asynchronous results cannot replace a newer revision.

Current source-stream limits include 16 pages loading/decoding/waiting for attachment, two actual page attachment attempts/frame, 64 MiB decoded source residency and 256 MiB estimated source GPU residency. Transport separately holds at most 16 queued requests and 32 replies; draining those queues does not bypass source-page admission. Hierarchy geometry/material caches have separate budgets. These counters are not total process/GPU memory. Admission skips blocked pages when a later page fits; priority eviction and aggregate pre-decode byte reservation remain open.

[ObjectLodPlugin](../crates/engine/src/object_lod.rs) owns visual-object scene selection after transform propagation. Streaming includes it for game/editor; collection previews can use it without database streaming. Streamed objects and editor previews share initial LOD construction, with the existing 12% hysteresis, 0.25–4 scale clamp and 32 switches/frame. Residency reads LOD telemetry through accessors. Omitting it in standalone composition leaves the initially attached scene; it does not unload visuals.

The [cover planner](../crates/terrain_render/src/lod/mod.rs) finds edge neighbours by walking the quadtree (up for coarser, down through split nodes for finer; [neighbours](../crates/terrain_render/src/lod/neighbours.rs)) rather than testing every pair. It produces identical covers with about 70× less work, so budgets are no longer limited by pairwise checks. Desktop budgets are 2,048 patches, 4M triangles, 512 metadata requests per plan and a 256 MiB mesh cache; iOS keeps 512 / 1M / 128 / 128 MiB until measured on a phone. Plans run on the async compute pool whenever the view or contact demand changes, from snapshots of their inputs (descriptors are shared and copied only if a reply lands mid-plan); `TerrainLodStats` reports their count and last duration (about 6 ms at the full desktop budget on M2 Max). A plan starts only while no target is staged, so the drawn cover and the descriptors it reads cannot be replaced or evicted before its result applies; live authoring cancels a running plan. A plan equal to the drawn cover stages nothing. Each plan is followed by a staged morph, so a cold view grows by about 90 patches every two seconds. Plans return missing metadata most urgent first and the engine loads 128 keys per plan, so actor and grass contact always precede visual refinement. A blocked root balance requests every missing split in one plan. The descriptor table holds 12 entries per patch of budget (24,576 on desktop): the drawn and staged covers, their ancestors and loaded children. It must never fill, or new ground stops loading. Descriptors and decoded samples that leave the cover stay in small least-recently-used caches (4,096 descriptors, 8 MiB of samples). A new cover evicts cached samples before its budget is checked. Each plan requests every missing descriptor in batches of 128, with up to 12 database queries and 8 mesh builds in flight. Refining a patch needs its four children, so one batch per plan grew a cover by only about 100 patches per plan-and-morph cycle. A moving view re-plans at most 10 times a second, except while drawn ground does not yet satisfy contact demand. The planner keeps its node sets in fixed-seed hash sets beside the ordered cover, and a morph's common cover walks ancestors (0.4 ms for two full covers, from 8 ms pairwise). Contact checks for grass pages and actors use an index of the drawn cover's footprints and certificates, filed by node square. The index is rebuilt only when the cover or a running morph changes. Each morph indexes its old and new covers once, so the per-frame cost does not grow with the patch budget.

World views (the game camera and the editor's world camera) cull at `WORLD_VIEW_DISTANCE`, 20 km, matching the default haze visibility. Bevy's default of 1 km hid kilometre-scale terrain. Depth is infinite reverse-Z, so this only decides what is drawn; terrain cost is still bounded by the hierarchy's screen-error LOD.

In the normal hierarchy path, static-object residency uses a separate 192 m camera-to-cell-bounds radius in all directions. Camera frustum visibility only prioritizes loading; it must not retire off-screen trees that can cast shadows onto visible ground. Bevy performs camera and shadow-cascade mesh culling independently. The descriptor window covers the larger of grass contact and object visibility ranges, within the existing 4096-cell query budget. Grass contact and gameplay demand keep their own ranges. This replaces the three-cell object limit that reduced visibility to about 24 m in 8 m worlds. The final mesh LOD remains selected below its threshold; billboard/fade transitions are not implemented. The legacy diagnostic path retains its three-cell window. Source memory and attachment budgets still apply, so 192 m is a demand limit, not a guarantee under memory pressure.

The local material supports one/two active surfaces despite the data contract allowing eight slots. Albedo is sRGB; normal/AO/roughness and macro maps are linear. Prepared albedo and stochastic-buffer references remain available. Nearby detail blends to baked ground; material preparation must preserve shared borders and fallback behavior.

## Vegetation

The runtime joins compact vegetation fields with terrain surfaces, generates candidates on the GPU, and emits bounded indirect draw bins for single/split topology and high/low geometry. It does not store an entity or database row per blade. Stable ownership, seeds and thinning preserve placement across views; telemetry exposes capacity drops.

The [renderer entry point](../crates/vegetation_render/src/renderer.rs) owns render-world composition and resource initialization. Internal modules separate CPU/WGSL layouts (`gpu_types`), CPU scene/LOD packing (`packing`), fixed index templates (`topology`), allocation/bind groups (`buffers`), pipeline specialization (`pipelines`), uploads/view inputs (`prepare`), cached placement dispatch (`generation`), opaque queue/draw (`draw`), and optional counter readback (`telemetry`). Candidate caching, blade preparation, temporal rendering and asynchronous canopy work retain their existing owners. Scheduling remains explicit at composition, including temporal dependencies and the iOS readback exclusion; these modules are not independently removable plugins.

Placement, source acceptance and per-frame blade deformation use separate caches. Wind phase must not invalidate source acceptance/placement unnecessarily. Prepared-blade overflow evaluates the original vertex path rather than dropping grass. Tests compare accepted instance multisets and rendered output, not append order alone. A scene revision uploads only the samples of pages that arrived or changed. `WorldVegetationPlugin` gives every page a content key, renewed when its field or terrain page changes and kept across rebases. [Page slots](../crates/vegetation_render/src/renderer/page_slots.rs) keep each keyed page's surface and coverage samples at a fixed range and free ranges when pages leave. Work items, species choices and species depend on the whole resident scene, so they are rebuilt each revision; they are small. Scenes without keys, such as editor previews and fixtures, are packed in full, as before. The acceptance cache is still rebuilt after every revision; keeping it for unchanged pages was not worth the work, since its measured saving is ~0.05 ms.

[WorldVegetationPlugin](../crates/engine/src/world_vegetation.rs) composes the renderer, published field/terrain joining, logical LOD focus and ground-canopy integration. The game installs it explicitly after world streaming; F1 applies settings before its update set. `VegetationSceneState` and `VegetationView` name the production render snapshot and camera opt-in. The serialized `VegetationDebugSettings` type remains unchanged for saved-study compatibility; its production and diagnostic fields still share one resource.

Game and editor share terrain-to-vegetation conversion and [GroundCanopyPlugin](../crates/engine/src/world_vegetation/canopy.rs). The editor retains authority over accepted draft catalogs/coverage and workspace selection. Terrain and vegetation keys match by space/cell/LOD and extent, ignoring their different page domains. Source joining continues while grass rendering is disabled, and clears stale pages when the world/catalog disappears. Joined in-place edits invalidate the snapshot; unrelated terrain pages do not.

The canopy cache keeps one immutable source snapshot plus per-tile indices. It compares actual nearby sources, including relief, before accepting bake results. World/origin/catalog changes, material replacement and unload release affected masks and cancel jobs. Disabling canopy detaches coverage and cancels jobs, retaining valid resident masks for reuse; source edits are checked before reattachment. Scheduling remains capped at two jobs after 0.35 seconds of source settling. Canopy updates run in `Update`, before terrain material preparation in `PostUpdate`. This replaces the two separate game/editor caches; no performance improvement has been measured.

[TreeWindPlugin](../crates/engine/src/tree_wind.rs) is installed explicitly by game/editor composition. It reads the existing `VegetationWind` direction, strength, gust field and phase; the vegetation renderer remains the clock owner, including external editor/replay transport. `TreeWindResponse` supplies the separate canopy/leaf response in metres. glTF materials opt in with `extras.yarra_wind = "foliage_uv1_v1"`; UV1 stores `(flutter, branch)` weights. Only tagged static, alpha-masked meshes are converted, with no path-name/prefab heuristics or database schema change. The pack exporter writes the tag for every foliage LOD and leaves bark rigid.

Tree materials extend the existing cloud-shaded PBR material, preserving textures, alpha clipping, normal maps and cloud transmission. Tagged foliage explicitly opts into that pipeline in isolated collection studies, where the study atmosphere disables cloud transmission; unrelated study materials retain their ordinary path. Conversion follows cloud material conversion and retries until scene dependencies and bounds exist. Instances share cached materials, source edits propagate, and unloading scenes releases the cache's references. Mesh bounds include the maximum allowed deformation. One shared 96-byte GPU buffer carries current/previous wind poses, so time updates do not rewrite per-instance transforms or dirty every material. Independently reduced f64 phase offsets preserve the field across floating-origin rebases.

Colour, depth and shadow passes evaluate identical tree geometry. The motion-vector prepass evaluates the previous model matrix with the last GPU-submitted wind pose, including its settings and origin; it does not reconstruct history from a time delta. This supports MetalFX Temporal and Bevy temporal consumers, paused/scrubbed transport and wind toggles. PostUpdate replay producers run before `TreeWindSystems`. New LOD topology still uses the renderer's ordinary history rejection; this does not implement LOD crossfading or guarantee shimmer-free foliage. A native GPU regression checks animation, pause, zero weights, disable and rebase cases, and the game path has been exercised with MetalFX Temporal.

Canopy shading is a shared artistic treatment of ground and lower blades, not physical grass self-shadowing. Source-boundary/coverage bakes run asynchronously with revision checks and bounded scheduling. Shading controls must not trigger unrelated placement/pose rebuilds. Grass casting onto ground remains unresolved; previous proxy casters were removed after visual rejection.

## Atmosphere and presentation

One authored atmosphere/weather profile belongs to each world space. Pure evaluation lives in `world`; the Bevy adapter owns sky, directional/ambient illumination and haze. The game advances session time; editor studies/preview transport can temporarily own it. Restoring a workspace must restore the correct owner and camera environment.

The [sky composite](../crates/atmosphere/src/sky.rs) draws everything between the camera and the scene in one pass over the resolved HDR image, after the main passes: the physical sky and sun/moon disks and aerial perspective from Bevy's atmosphere tables, the cloud layer and weather fog. Bevy still computes those tables and lights surfaces through them; only its own sky pass is replaced, by a no-op in the same schedule slot (found as the only system whose sole constraints are after the opaque pass and before the transparent pass, apart from the public transmissive pass). That pass drew into the multisampled colour target, so multisample colour had to be stored and reloaded every frame, and it fogged whole pixels from one depth sample. The composite reads every depth sample: sky samples get the sky's light and geometry samples the haze of their own distance, and the resolved image is multiplied by the transmittance averaged over geometry samples only, because sky samples hold the black clear colour. Pixels whose samples share one distance are shaded once. Transmittance is per channel through dual-source blending where the GPU supports it. The composite needs sampled depth, which Bevy requests only for atmosphere views, so `WorldEnvironmentView` cameras request it themselves. Aerial-perspective transmittance integrates the medium's extinction along the camera-to-surface segment (Simpson's rule over Bevy's full-precision density table, bound at 5/7). Bevy's segment lookup divides two whole-atmosphere transmittances that underflow its half-float table for near-horizontal ground rays, which drew coloured horizontal streaks on distant terrain. The F1 sky switch stops the composite drawing sky and haze but keeps Bevy's tables, so surface lighting does not change with it.

Balanced clouds use a 2048×256 azimuth × elevation sky panorama (square-root elevation warp, rows along the horizon) refreshed a few rows every frame, four complete refreshes per second at any frame rate. The sky composite cross-fades the two latest complete refreshes while a third image is refreshed, so clouds change continuously rather than in 4 Hz steps behind a moving refresh seam; High retains per-frame half-resolution rendering. Cloud altitude, field size, seed or enablement changes, teleports and resume require a full refresh; coverage, density, erosion and thickness (weather) and normal evolution update progressively. Cloud Off skips cloud tracing and shadow passes but preserves weather fog, weather's ambient response and some shared bookkeeping.

Game weather is [pure data in `world`](../crates/world/src/weather.rs): Clear/Scattered/Overcast/Rain/Storm presets, a weighted random sequence with hold/transition durations, continuous blending from the current values and a wetness integrator. Each world's `AtmosphereProfile::weather` holds its authored presets and sequence (persisted as the `WTH1` atmosphere extension after `CLD1`; untouched profiles keep their exact previous encoding), defaulting to the built-in values. The game adopts published edits live without restarting the sequence. The editor previews any preset, with a chosen wetness, over the edited or published profile; editor-owned atmospheres apply weather only as that explicit preview, and studies never do. Rain shelter and grass ambient gain are game-only, so editor previews rain under trees. The [engine adapter](../crates/engine/src/weather.rs) advances it in the game only (`AtmosphereOwner::Game`) and overlays it on the authored profile: cloud shape, daytime exposure and skylight colour through `AtmosphereState::effective_profile`, the grass ambient bound through `VegetationAmbientGain` (exposure adaptation, since grass lighting is bounded in exposed units), and the shared wind through `VegetationWind` strength, gusts and `rate`. Grass, trees and cloud drift share the authored cloud wind direction while weather is active. Weather changes the wind clock rate rather than `speed`, because phase is `time × speed`. Reduced visibility is not written into Bevy's scattering medium: its half-float transmittance tables divide values that underflow below a few kilometres and produced NaN streaks. During a weather change each region of the cloud field blends from the previous coverage, extinction and erosion at its own time (a noise-driven arrival over ~40% of the change) instead of one global threshold; cloud shadows share the same density function. Weather fog instead adds the missing extinction, lit by desaturated ambient light, per depth sample in the sky composite, outdoors only. `--weather authored`, the default for profiles, repros, captures and smoke runs, presents the profile unchanged. F1 A/B captures pause the weather clock and record the weather.

[Precipitation](../crates/atmosphere/src/precipitation.rs) draws rain as instanced camera-facing streaks in three camera-anchored boxes (near, mid, far) that wrap a world-fixed drop lattice. Positions come from hashes plus a CPU-accumulated fall offset, so there is no per-drop state and wind changes never make drops jump. Streaks follow drop velocity relative to the smoothed velocity of `PrecipitationReference`, which the game sets to the camera's follow target so orbiting does not tilt the rain (teleports and origin rebases ignored; free cameras draw unstretched streaks), keep at least one pixel of width with proportionally reduced alpha, fade near the lens and with weather fog, and use a soft test against scene depth. The pass runs between `EarlyPostProcess` and `PostProcess`: after Temporal reconstruction (no ghosting, output resolution) or on the resolved MSAA image, and before bloom and tone mapping. Wetness from `AtmosphereState` reaches every surface through `CloudParams::weather`: the shared PBR adapter darkens albedo and lowers roughness on sky-facing surfaces, and grass darkens its body colour.

The [open sea](../crates/engine/src/ocean.rs) is render-only. A world space's optional `sea_level` (stored in both databases) places one flat, opaque, glossy surface that follows the active world view out to the view distance; terrain below it forms the shore. It is hidden when the space has no sea level or no world view is active (editor studies). The shared PBR conversion gives it cloud shadows and rain. It is a placeholder: waves, shore foam, transparency, swimming, lakes and rivers are not implemented.

[Rain shelter](../crates/atmosphere/src/shelter.rs) is a 256² top-down map (0.5 m texels, 128 m around the camera) of the highest object top above each texel and its coverage. Any placed object shelters the ground below its top, so trees, shrubs and rocks need no tagging: streamed objects carry an `ObjectFootprint` from their largest LOD bounds, and the [engine](../crates/engine/src/weather.rs) rebuilds the map while rain or wetness needs it, after moving 16 m, on origin rebases and (throttled to 0.5 s) when objects stream. Materials bind it at 123 beside the cloud inputs; rain streaks, splash placement, surface wetness and puddles all use the same bilinear lookup. Splashes are spawned on the CPU on resident terrain in a disc around the ground the camera looks at, at constant density per square metre (skipping steep and sheltered ground), into a 512-entry ring buffer with the terrain normal. Each draws a ripple ring lying on the surface (strong on wet ground, faint on dry) and four droplets thrown in a cone that fall back under gravity, hidden behind nearer geometry such as grass. [Puddles](../assets/shaders/weather/ground_wetness.wgsl) follow the relief: the cooker stores each ground composite texel's hollowness (depth below the ground within 1.5 m, saturating at 15 cm; averaged into coarser pages) in the colour alpha, which was always opaque. As ground soaks, water rises into road ruts and dips deepest first; when soaked, hollows about 4 cm deep hold water, and a few sparse noise puddles remain on open flat ground. Only wet ground within 80 m reads the value: one extra texture read, plus a detail-tile lookup where the close surface cache supplies colour. Composite version 1 pages decode with no hollowness until re-cooked, and the legacy terrain path uses noise puddles. Ripple rings animate while rain falls; only the terrain shaders call it.

Game defaults are 50% of physical width/height, 4× MSAA, native-resolution UI, Auto upscaling, Balanced grass/clouds and optional counters off. Auto uses MetalFX Spatial when supported, otherwise Linear. Explicit Linear samples the scene directly during UI composition. MetalFX Temporal is an integrated, selectable game backend: it replaces MSAA, requires mesh depth/motion, writes grass color/motion/final depth, reconstructs HDR before full-size postprocessing, and resets history on discontinuities. Motion excludes jitter; exposed HDR uses a unit exposure hint. Recorded performance and moving-grass quality issues remain unresolved; these are follow-up issues in an implemented feature, not missing temporal integration. See the ledger.

`MsaaColorStorePolicy::Automatic` discards multisample color only when later consumers permit it; depth is retained. New passes loading that color must request Preserve or extend the consumer check. Atmosphere views qualify only while `BevySkyPassReplaced` confirms Bevy's sky pass is gone. This adapts Bevy's opaque schedule, as the sky composite adapts its sky pass; both must be rechecked on upgrades. The [wgpu-hal patch](../third_party/wgpu-hal/YARRA_PATCH.md) supplies the Metal minimum presentation interval for frame pacing; it is not obsolete vendored experimentation.
